# Serial hardening: journal initialization and recovery

This is the first feature acceptance gate after the ten-area foundations PR.
The feature is the local journal's initialization, integrity, revision ownership
and recovery boundary, including adapter startup and CLI snapshot import.
Receipt-based ingestion, external projection transactions, native KV, retrieval
policy and agent benchmarks are subsequent gates; this review does not accept
those features or declare the platform production-ready.

## Independent review and corrections

A builder agent changed journal internals. The primary agent built the independent
process harness and fixed adapter/import ownership. A separate grading agent
reviewed the implementation and ran additional independent transition oracles.
Acceptance requires a feature-specific score of at least 9.5/10 and no known
silent-overwrite or concealed-corruption path. A score is engineering review
evidence, not proof against every failure or hardware condition.

Final independent grade: **9.5/10 — accepted for this feature**. The final focused
harness passed **50 tests**. The [review record](artifacts/journal-review-2026-09-12.json)
contains category scores, evidence and SHA-256 hashes of the accepted source files.
Final-commit CI is a separate merge gate. The next serial feature is semantic
checkpoint publication, retention and worker lifecycle; native KV remains excluded.

The initial implementation was held from acceptance for these concrete findings:

- Two first-time constructors could race on existence and schema creation.
- Revision zero and unchecked historical decisions could conceal committed loss.
- Archived snapshots and SQL schema objects were insufficiently validated.
- Startup could associate an old payload with a peer's newer revision, permitting
  a later overwrite; CLI import similarly lacked a revision-zero CAS.
- Initialization, identity publication and export of lock paths needed explicit
  boundaries; mutable caller input could be serialized inconsistently.

The resulting implementation serializes bootstrap through one persistent lock,
freezes writes before I/O, verifies history and historical snapshots, preserves
read revision identity, and rejects corruption at every journal entry point.
The harness additionally caught an evidence-runner error, which was corrected
and covered by an executable runner regression before acceptance.

## Executable evidence

`test_journal_hardening.py` covers actual process termination at seven initialization
boundaries, eight separate clients racing to create one journal with an independent
acknowledgement history, schema/history/snapshot corruption, unsafe export paths,
startup/import interleavings, and a schema-1 fixture generated by commit
`b8626b73b2caeab2a7c25353d11aa526adf777a2`. Existing journal tests retain all seven
transaction kill points, quota-full rollback, serialization failure and CAS stress.

```sh
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 DML_SKIP_VENV_REEXEC=1 \
  python -m pytest dml_core/tests/test_journal_hardening.py dml_core/tests/test_production_foundations.py
DML_STRESS_CLIENTS=256 OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 \
  python -m pytest dml_core/tests/test_production_foundations.py::test_concurrent_clients_use_compare_and_swap_without_lost_updates
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 \
  python -m scripts.journal_history_benchmark --output production-artifacts/journal-history.json
```

The full local core/Hermes/wrapper suite passed on Python 3.12.14 after the runtime
changes; the separate 256-client CAS stress also passed. The new regression file
was rerun after final reviewer-requested schema cases and the harness fix. Ruff
and maintained mypy including the journal (43 source files, local type target
3.12) passed. These are local Linux results. The updated CI includes the new
regressions in all six portability lanes and publishes history-cost evidence;
remote results must be checked on the final commit.

## History cost and remaining limits

The [raw local history-cost artifact](artifacts/journal-history-2026-09-12.json)
contains ten warm samples per operation at each milestone over a fixed ten-record
lattice. Metadata commits grow the history without growing the live corpus.

| Revisions | Read p50 | Stamp p50 | Unchanged save p50 | Reopen p50 |
| --- | --- | --- | --- | --- |
| 1 | 1.10 ms | 1.04 ms | 1.19 ms | 1.24 ms |
| 64 | 2.20 ms | 2.19 ms | 2.25 ms | 2.30 ms |
| 256 | 5.74 ms | 5.72 ms | 5.60 ms | 5.58 ms |
| 1,000 | 19.19 ms | 22.31 ms | 19.49 ms | 19.71 ms |

Whole-history verification is visibly expensive: even a stamp scans every prior
decision. It remains an explicit long-horizon performance limitation. This run
does not qualify 10k/100k history, HTTP concurrency, agent success, distributed
filesystems, or hardware power-loss behavior. Unkeyed hashes do not defend against
coherent rewriting of state and checksums or replay of a complete older database.

Process death before schema commit preserves an incomplete schema-0 file and
requires explicit recovery or a new location. Only a fully validated schema-1
database may finish missing-marker publication. Keep all identity and coordination
files with the database, and never delete lock files while clients are active.
The [production contract](contracts/production-v1.md) is the recovery reference.
